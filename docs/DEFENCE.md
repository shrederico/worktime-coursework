# Как объяснить проект

Платформа позволяет назначать задачи сотрудникам и учитывать затраченное время.
Руководитель видит команду, сотрудник — свои задачи и записи. Главная задача
курсовой — показать настройку и администрирование контейнерной инфраструктуры.

## Пять компонентов

Nginx принимает запрос браузера и передаёт его Django. Django проверяет права,
обрабатывает форму и обращается к PostgreSQL. Prometheus периодически запрашивает
показатели приложения, Grafana показывает их на панели. У каждого компонента
отдельная роль; контейнеры не добавлены только ради количества.

Dockerfile описывает сборку образа приложения. Образ — подготовленный шаблон,
контейнер — запущенный экземпляр. Compose описывает совместный запуск сервисов,
сетей и томов на одном Docker Engine. Том хранит базу независимо от контейнера.
Восстановление копии проверяется отдельно от простого перезапуска.

## Что показывают кластеры

В Swarm есть manager и worker с отдельными Docker Engine. Manager распределяет
две реплики приложения между узлами. При остановке реплики создаётся замена.
Учебные узлы находятся в контейнерах на одном Mac: отказ самого Mac останавливает всё.
База одна, поэтому отказ узла хранения не покрывается этой схемой.

В Kubernetes есть control-plane и два worker. Deployment поддерживает заданные
две реплики приложения. Pod — единица запуска контейнеров Kubernetes. Service
даёт постоянный сетевой адрес группе Pod, даже когда отдельный Pod заменён.
Проверка readiness обращается к health: приложение выполняет SELECT 1 в базе.
Для проверки указан Host localhost, чтобы не ослаблять ALLOWED_HOSTS Django.

## Последовательность демонстрации

1. На localhost:8080 войти как manager, назначить задачу anna.
2. Войти как anna, изменить статус и записать время. Показать личный отчёт и CSV.
3. Войти как manager и показать общий результат. В Grafana на порту 3000 показать метрики.
4. Для Swarm открыть localhost:8081 и показать два узла и две реплики через
   docker compose -f infra/swarm/lab.yaml exec -T manager docker node ls
   и аналогичную команду docker service ps worktime_app.
5. Показать docs/swarm-results.json: реплика до остановки и после восстановления.
6. Для Kubernetes использовать kubeconfig .lab/kubeconfig, показать kubectl get nodes
   и kubectl -n worktime get pods -o wide. Результат замены Pod — kubernetes-results.json.
7. Показать local-pipeline-results.json: новая версия образа, тесты и обновление.

## Доставка обновлений

Локальный процесс собирает новый образ, запускает тесты с отдельной тестовой БД,
загружает образ на оба узла и последовательно заменяет реплики. Тег версии
позволяет отличить новое приложение от прежнего. Локальный запуск ручной.
Workflow GitHub Actions предусматривает запуск по push, публикацию в GHCR и
развёртывание через runner. Его реальный запуск требует репозитория и runner;
наличие файла workflow не является доказательством удалённого CI/CD.

## Чего не утверждать

Несколько контейнеров не означают несколько физических серверов. Две реплики
приложения не делают базу отказоустойчивой. Зелёный тест не заменяет проверку
пользовательского сценария. Учебная установка не является публичным сервисом
для реальных сотрудников. Цифры демонстрации относятся к учебным данным.
