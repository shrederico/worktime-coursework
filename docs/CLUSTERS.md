# Кластерные этапы

## Готовый локальный стенд на Mac

Swarm: `python3 scripts/swarm_lab.py`. Создаются только manager и worker проекта
worktime-swarm-lab, основной Docker Engine не переводится в Swarm. Для вложенных
Docker Engine используется официальный образ docker:dind с privileged; сокет
Docker компьютера внутрь не монтируется, управляющий TCP-порт не публикуется.
Это учебный стенд, а не рекомендуемая архитектура промышленной эксплуатации.
Демонстрация: http://localhost:8081, Grafana: http://localhost:3001.
Основная платформа Compose остаётся на портах 8080 и 3000.

Узлы имеют отдельные Docker Engine и тома. Реплики app ограничены одной на узел.
Стандартный лимит памяти 512M в этом вложенном стенде отключается через
APP_MEMORY_LIMIT=0 из-за ограничений cgroup Docker Desktop; обычная конфигурация
Swarm сохраняет лимит. Ни настройки ядра, ни настройки Docker Desktop не меняются.

Проверка доставки обновления: `python3 scripts/local_pipeline.py`.
Процесс собирает образ с новым тегом, выполняет тесты PostgreSQL, доставляет
образ на оба узла, обновляет реплики последовательно и проверяет HTTP-доступность.
Он запускается вручную; автоматический запуск по push относится к отдельному
workflow GitHub Actions и требует подключения репозитория и runner.

Kubernetes использует отдельный kubeconfig: `.lab/kubeconfig`. Все команды для
него запускаются с `KUBECONFIG="$PWD/.lab/kubeconfig"`, чтобы не менять пользовательский
контекст. Kind установлен только в `.lab/bin/kind`. Для остановки учебных стендов
без удаления данных можно остановить контейнеры worktime-swarm-lab и три узла
kind с префиксом worktime-. Основная платформа имеет контейнеры worktime-app-1,
worktime-db-1 и т. д.; их при остановке кластерных демонстраций не затрагивают.

Это инструкция для следующего этапа, не протокол уже выполненного развёртывания.
Compose, Swarm и Kubernetes используют одно приложение, но разные описания запуска.

## Swarm

Стенд: два Linux-узла (manager и worker) с Docker Engine, доступные друг другу.
Один manager достаточен для учебной демонстрации, но не обеспечивает отказоустойчивость
управляющего узла. Две реплики приложения не делают единственную базу отказоустойчивой.

1. На manager выполнить `docker swarm init --advertise-addr <IP_MANAGER>`.
2. На worker выполнить команду присоединения, которую выведет manager.
3. На manager проверить `docker node ls`. Оба узла должны иметь состояние Ready.
4. Назначить одному узлу хранения метку: `docker node update --label-add worktime.data=true <NODE>`.
   Метку нужно назначить ровно одному узлу: локальные тома базы и мониторинга остаются на нём.
5. Подготовить `.env`: указать адрес стенда в ALLOWED_HOSTS и полный origin в
   CSRF_TRUSTED_ORIGINS. Пароли для стенда должны быть собственными.
6. Собрать и отправить образ приложения в доступный обоим узлам реестр. Указать
   уникальный тег, например хеш коммита. Для узлов разных архитектур нужен multi-platform образ.
7. Выполнить `APP_IMAGE=<адрес_образа:тег> sh scripts/deploy_swarm.sh`.
8. Проверить `docker stack services worktime`, `docker service ps worktime_app`,
   открыть адрес manager на порту 8080. Порты 8080 и 3000 в Swarm доступны на узлах;
   стенд должен находиться в доверенной учебной сети, не на открытом публичном IP.

Конфигурации Nginx и мониторинга передаются как Swarm configs. Скрипт вычисляет
CONFIG_VERSION по содержимому файлов: изменения получают новые имена configs.
Это позволяет обновлять настройки без попытки изменить неизменяемый объект Swarm.
Старые configs сохраняются для отката; вручную удалять их следует только после
проверки, что они не используются сервисами.
Значения окружения видны администратору Docker; `.env` не следует включать в отчёт или скриншоты.

Проверки: масштабирование app до трёх реплик; остановка одной реплики; обновление
образа с уникальным тегом; проверка доступности и сохранности записей. Для проверки
переноса между узлами отключают worker с экземпляром app. Отказ узла с локальной БД
не покрывается этой архитектурой и должен быть честно указан как ограничение.

## Kubernetes

Для локальной учебной демонстрации можно использовать kind: узлы Kubernetes
работают внутри контейнеров Docker. Это несколько логических узлов на одном Mac,
а не несколько физических серверов. Утилита kind пока не устанавливается автоматически.

1. Установить kind по официальной инструкции для своей архитектуры.
2. Создать отдельный кластер: `kind create cluster --name worktime --config infra/kubernetes/kind.yaml`.
3. Проверить выбранный контекст: `kubectl config current-context` должен показать `kind-worktime`.
4. Выполнить `kind load docker-image worktime:local --name worktime`.
5. Выполнить `bash scripts/deploy_kubernetes.sh`.
   Для образа из реестра передать `APP_IMAGE=<адрес:уникальный-тег>` перед командой.
   Реестр должен быть доступен узлам; приватный реестр требует настройки imagePullSecrets.
   Для локального образа после пересборки повторить kind load docker-image.
6. Выполнить `kubectl -n worktime port-forward service/proxy 8082:80` и открыть
   http://localhost:8082. Для Grafana: `kubectl -n worktime port-forward service/grafana 3002:3000`.

Миграции выполняет отдельный Job, app запускается в двух репликах. База хранится
в PVC с StorageClass по умолчанию. В kind локальное хранилище не переносится на
другой узел при отказе. История мониторинга в Kubernetes намеренно временная;
панель Grafana восстанавливается из ConfigMap. В Compose история мониторинга постоянная.
Демонстрационные данные Kubernetes независимы от базы Compose.

Проверки: `kubectl -n worktime get pods -o wide`; удалить один Pod приложения
и убедиться, что Deployment создал замену; повторить пользовательский сценарий.
Не удалять namespace или PVC ради проверки восстановления экземпляра приложения.

## CI/CD

Файл workflow выполняет тесты с PostgreSQL, собирает образ для ARM64 и AMD64,
публикует его в GHCR с тегом SHA коммита. Развёртывание выполняется на Linux manager
через собственный GitHub runner с меткой `worktime`. На runner нужны Docker, Python 3, curl,
доступ к manager и возможность запускать Docker без интерактивного sudo.

Для включения нужны личный репозиторий GitHub, runner, secret `DEPLOY_ENV` с
содержимым `.env` стенда и repository variable `DEPLOY_ENABLED=true`. Значения
паролей нельзя вставлять в workflow. Для собственного runner использовать закрытый
учебный репозиторий. До подключения runner этап deploy явно пропускается.

Автоматическая проверка pull request выполняется на GitHub-hosted runner.
Развёртывание предусмотрено только из main; одновременные запуски сериализуются.
Публикация репозитория и регистрация runner в этой версии не выполнялись.
Успешной реализацией CI/CD будем считать реальный запуск всех этапов и доступность
новой версии на стенде, а не только наличие YAML-файла.
